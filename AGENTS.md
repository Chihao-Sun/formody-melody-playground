# Formody Repository Instructions for AI Assistants

## Project identity and direction

- Use the canonical project name **Formody · 拨形见声**. Do not revert to the older two-character label.
- Formody is a browser-based art playground where genuine mathematical rules become interactive visuals and sound.
- The current prototype is a single-Seed regular-pentagon Outer Billiards study with a monophonic phrase. Multi-voice music, additional mathematical studies, final visual language, and real iOS Safari validation remain future work.
- The visual and musical direction is still being explored. Treat concepts and mockups as proposals until the owner confirms them.
- Preserve mathematical truth: a musical loop does not prove the mathematical orbit is periodic; a finite search without a repeat does not prove an orbit is unbounded; do not describe a visual warp as genuine hyperbolic geometry.

## Work with the project

- Read the README and the relevant files in `docs/` before changing project behavior or public claims.
- The owner's latest explicit decision supersedes older notes. When an old project document conflicts with a confirmed decision, correct the relevant public project note as part of the same task.
- Keep confirmed decisions, proposals, and deferred ideas distinct. Do not silently turn a recommendation into a product requirement.
- Keep one main outcome per task and follow the requested task level. Do not expand a small task into unrelated features.
- Preserve existing working behavior. Run the relevant checks for code changes and report exactly what was and was not verified.
- Follow `docs/conversation-workflow.md` for chat titles, task briefs, and cross-chat handoffs.

## Public repository and community

- This repository is public. Every tracked change and commit is public and may remain in history.
- Never commit credentials, tokens, private conversation transcripts, personal contact details, identifiable user research, private operational logs, or unreleased private notes.
- Keep private material outside this repository or in a separate private store. `.gitignore` is only an accidental-commit guard, not secure storage.
- Follow `docs/open-source-and-promotion.md` for public/private boundaries, promotional claims, and open-source readiness.
- Describe only behavior supported by current code or dated evidence. Do not claim multi-voice support, real iOS Safari acceptance, a mathematical proof, or a published open-source license unless it is verified.
- Do not choose a project license or state that code contributions are open until the owner confirms the license and the repository includes the required project terms.
- Keep source commits, saved Site versions, live deployments, and public announcements as separate records. Report each accurately.
