# Formody · 拨形见声｜对话组织规范

## 目的

本对话作为项目总览与规则中枢；新开的对话按工作主题拆分。这样项目方向集中维护，研究、设计和开发讨论也各自有完整上下文。

## 对话分工

- **总览与规则**：维护项目目标、已确认决策、跨模块优先级、规则和当前阶段。只有影响整体方向的结论需要回到总览对话汇总。
- **专题对话**：一次聚焦一个主要问题和一个预期结果，例如灵感研究、数学与交互、UI 设计、音乐设计、开发测试或发布验证。
- **提案与决定分开**：专题对话里探索出的候选方案先标为“待讨论”；用户确认后再记为项目决定。临时建议不自动变成长期规则。

## 对话标题

统一使用：

`Formody｜<领域>｜<具体主题>`

标题中的项目名前缀只使用英文名 `Formody`；中文正式名称 `Formody · 拨形见声` 继续用于项目品牌、README、文档和产品内容。

本总览对话建议标题：`Formody｜总览与规则`

专题领域优先使用：`研究`、`产品与数学`、`UI 设计`、`音乐设计`、`开发与测试`、`体验验证`、`发布`。

标题保持短而稳定，不加日期；任务等级（如 LV1）写在开场信息里，除非需要区分同主题的并行任务。一个对话结束后，不继续塞入无关主题。

示例：

- `Formody｜研究｜参考作品的叙事与视觉`
- `Formody｜UI 设计｜整体视觉语言`
- `Formody｜音乐设计｜多声部与节奏`
- `Formody｜开发与测试｜Loop 捕捉`
- `Formody｜体验验证｜iOS Safari`

## 新对话开场信息

按任务需要填写，不必重复整份项目背景：

```text
项目：Formody · 拨形见声
本对话目标：<一个主要目标>
任务等级：<如适用，例：LV1>
当前状态依据：<相关 README、docs 文件、提交或明确提供的摘要>
已确认边界：<本任务必须保留的决定>
完成标准：<怎样算完成>
```

新对话先读取与任务直接相关的项目资料；若用户提供了更新的决定或进度，以较新的明确决定为准，并标注它是确认项还是待讨论项。

## 结束时的交接

专题对话结束时，向总览对话带回简短交接：

1. 得出的结论，以及哪些已确认、哪些仍待讨论。
2. 实际改动的文件和提交（如有）。
3. 已执行的检查及结果；未检查的内容也明确写出。
4. 当前阻塞和建议的下一步。

## 当前项目锚点

- 正式名称：**Formody · 拨形见声**。
- 作品目标：让真实数学规律通过交互转化为动态画面与可听见的音乐体验。
- 当前原型是单 Seed 外台球体验；多声部、节奏变化、最终视觉语言和真实 iOS Safari 验收仍是后续工作。
- 项目级决定以用户最新明确表述为准；旧文档与新决定冲突时，先按新决定工作，并在项目资料中修正冲突记录。

## AI 对话与执行规范

- 开始工作前读取与任务直接相关的项目资料；不要只凭旧对话印象猜当前状态。
- 以用户最近明确确认的决定为准。把事实、推断、提案和待决定事项分开写；未确认的建议不自动升级为项目规则。
- 一个专题对话聚焦一个主要目标。执行中发现跨模块决定时，先说明影响，再把确认后的结论带回总览对话。
- 对范围清楚、可逆且已获授权的任务直接推进；只有当缺失信息会实质改变结果、范围或隐私/公开边界时才澄清。不要重复询问用户已经明确给出的选择。
- 按用户给定的任务等级控制改动范围，不把 LV1 等级的任务扩展成大型重构。
- 如实区分已完成与待完成；没有实际执行的测试、设备检查、发布和用户验证，不得写成已通过。
- 对外文案可以更清楚、更有吸引力，但必须以已验证的产品能力为依据；推广表达不能替代事实核验。
- 私人对话全文和个人资料不复制到公开仓库。需要社区共享时，提炼去个人化的通用规则，并遵守 `docs/open-source-and-promotion.md`。

## 实时更新与 Git 同步

- 本规范是持续维护的项目规则。负责人明确确认新规则、修正旧决定，或发现旧规则反复造成误解时，在同一项工作中更新相关文档。
- 只有已确认的决定进入规范；探索中的方向标为“待讨论”，延后事项标为“后续”。
- 可供社区复用的通用规则进入公开 Git；个人偏好、私人对话、账号与运营细节进入仓库外的个人私密同步空间。
- 更新公开资料前检查新增内容是否含私人信息，并在下方记录日期和改动范围。
